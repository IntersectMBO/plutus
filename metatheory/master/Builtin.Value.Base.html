Currency symbols, token names and their order

In Cardano, a value is an amount of Ada together with amounts of other assets, called native tokens. A token is identified by its currency symbol and its token name, both represented as bytestrings:

  • the currency symbol identifies the minting policy
  • the token name distinguishes the tokens minted under the same policy.

Various other names are used for these: for example the Cardano ledger and the Aiken language call currency symbols policy IDs and token names asset names.

CurrencySymbol : Set
CurrencySymbol = ByteString

TokenName : Set
TokenName = ByteString

We call the pair of a currency symbol and a token name, which identifies a token, a key.

ByteStrings are ordered lexicographically, as described in Builtin.ByteString.Order, and keys are ordered lexicographically by currency symbol, then by token name.

Key : Set
Key = CurrencySymbol × TokenName

_<ᵏ_ : Key → Key → Set
_<ᵏ_ = ×-Lex _≡_ BS._<_ BS._<_

The order on keys is a strict total order, since it is the lexicographic product of two strict total orders. compareᵏ decides it, and _≟ᵏ_ decides equality of keys.

<ᵏ-isStrictTotalOrder : IsStrictTotalOrder (Pointwise _≡_ _≡_) _<ᵏ_
<ᵏ-isStrictTotalOrder =
  ×-isStrictTotalOrder BS.<-isStrictTotalOrder BS.<-isStrictTotalOrder

_≟ᵏ_ : DecidableEquality Key
_≟ᵏ_ = ≡-dec BS._≟_ BS._≟_

compareᵏ : Trichotomous _≡_ _<ᵏ_
compareᵏ k k' with IsStrictTotalOrder.compare <ᵏ-isStrictTotalOrder k k'
... | tri< a ¬b ¬c = tri< a (¬b ∘ λ { refl → refl , refl }) ¬c
... | tri≈ ¬a b ¬c = tri≈ ¬a (≡×≡⇒≡ b) ¬c
... | tri> ¬a ¬b c = tri> ¬a (¬b ∘ λ { refl → refl , refl }) c

Values as sorted association lists

The quantity of a token in a value is the amount of that token the value holds. Quantities of Ada are counted in lovelace, a millionth of an Ada. Quantities are integers, and may be negative: for example, the tokens minted and burnt by a transaction are given as a single value, in which minted tokens have positive quantities and burnt tokens negative ones.

A value is a finitely supported map from keys to quantities: only finitely many tokens have a non-zero quantity. We represent it as a flat association list of entries, each a key with its quantity, which are compared by their keys (see Why a flat association list below).

Quantity : Set
Quantity = ℤ

Entry : Set
Entry = Key × Quantity

_<ᵉ_ : Entry → Entry → Set
_<ᵉ_ = _<ᵏ_ on proj₁

<ᵉ-trans : Transitive _<ᵉ_
<ᵉ-trans = IsStrictTotalOrder.trans <ᵏ-isStrictTotalOrder

The list is required to be well-formed, so that every value has exactly one representation:

  • the keys are strictly increasing (so there are no duplicates);
  • every quantity is non-zero.

Value∞ places no bound on the lengths of keys or on quantities; the bounds of the builtin type are imposed in Builtin.Value. This makes adding and negating values total, and gives them the structure of a commutative group (see Builtin.Value.Union.Properties).

NonZero : List Entry → Set
NonZero = All λ (_ , q) → q ≢ 0ℤ

≢-zero? : (q : Quantity) → Dec (q ≢ 0ℤ)
≢-zero? q = ¬? (q ℤ.≟ 0ℤ)

nonZero? : ∀ kvs → Dec (NonZero kvs)
nonZero? = all? (≢-zero? ∘ proj₂)

record Value∞ : Set where
  constructor mkValue∞
  field
    map : List Entry
    .<-keys : Linked _<ᵉ_ map
    .quantity-≢-zero : NonZero map

empty∞ : Value∞
empty∞ = mkValue∞ [] [] []

Why a flat association list

Grouping the entries of a well-formed list by currency gives a nested association list, which is closer to the concrete representation of values (see Builtin.Value.Nested). We use the flat list instead because:

  • its well-formedness is a single condition on the keys, while a nested list also needs every inner list to be sorted and non-empty, which every operation has to maintain;
  • most builtins act on individual tokens, which takes a single traversal of a flat list, and so do the proofs about them.

The few operations that need the tokens grouped by currency, such as policies and valueData, go through the nested representation, which is equivalent (see Builtin.Value.Nested.Properties).

Since every value has exactly one representation, values with the same quantities are equal (lookup∞-injective). The algebraic laws of values, such as the commutativity of their addition, are then natural extensions of the corresponding laws of the integers.

A value could also be a function from keys to quantities, but then proving that values with the same quantities are equal needs function extensionality, which is only provable in Cubical Agda. A function also does not list its tokens, which builtins such as policies need.

Setting the quantity of a token

insertEntry k q kvs sets the quantity at the key k in the sorted association list kvs to q: if k is present its quantity is replaced, and otherwise the entry (k , q) is added at the position that keeps the keys sorted.

insertEntry : Key → Quantity → List Entry → List Entry
insertEntry k q [] = (k , q) ∷ []
insertEntry k q ((k' , q') ∷ kvs) with compareᵏ k k'
... | tri< _ _ _ = (k , q) ∷ (k' , q') ∷ kvs
... | tri≈ _ _ _ = (k' , q) ∷ kvs
... | tri> _ _ _ = (k' , q') ∷ insertEntry k q kvs

insertEntry keeps the keys sorted, and a property of all entries holds after inserting (k , q) if it holds for (k , q).

replace-head
  : ∀ {k q q' kvs} → Linked _<ᵉ_ ((k , q') ∷ kvs) → Linked _<ᵉ_ ((k , q) ∷ kvs)
replace-head [-]     = [-]
replace-head (r ∷ l) = r ∷ l

insertEntry-linked
  : ∀ k q kvs → Linked _<ᵉ_ kvs → Linked _<ᵉ_ (insertEntry k q kvs)
insertEntry-linked k q []                _ = [-]
insertEntry-linked k q ((k' , q') ∷ kvs) l with compareᵏ k k'
... | tri< k<k' _ _ = k<k' ∷ l
... | tri≈ _ refl _ = replace-head l
... | tri> _ _ k'<k = linked-∷ kvs k'<k l
  where
    -- Inserting after an entry `e` smaller than `(k , q)` keeps it first.
    linked-∷
      : ∀ {e} kvs → e <ᵉ (k , q) → Linked _<ᵉ_ (e ∷ kvs)
      → Linked _<ᵉ_ (e ∷ insertEntry k q kvs)
    linked-∷ []                  r _        = r ∷ [-]
    linked-∷ ((k'' , q'') ∷ kvs) r (r' ∷ l) with compareᵏ k k''
    ... | tri< k<k'' _ _ = r ∷ k<k'' ∷ l
    ... | tri≈ _ refl _  = r' ∷ replace-head l
    ... | tri> _ _ k''<k = r' ∷ linked-∷ kvs k''<k l

insertEntry-all
  : ∀ {P : Entry → Set} k q kvs → All P kvs → P (k , q) → All P (insertEntry k q kvs)
insertEntry-all k q []                _        p = p ∷ []
insertEntry-all k q ((k' , q') ∷ kvs) (p' ∷ a) p with compareᵏ k k'
... | tri< _ _ _    = p ∷ p' ∷ a
... | tri≈ _ refl _ = p ∷ a
... | tri> _ _ _    = p' ∷ insertEntry-all k q kvs a p

insert∞ c t q v sets the quantity of the token t of the currency c in v to q, replacing the previous quantity, if any. q must be non-zero: setting a quantity to zero amounts to deleting the token, which is done by delete∞ (see below).

insert∞ : CurrencySymbol → TokenName → (q : Quantity) → .(q ≢ 0ℤ) → Value∞ → Value∞
insert∞ c t q nz (mkValue∞ m s z) =
  mkValue∞
    (insertEntry (c , t) q m)
    (insertEntry-linked (c , t) q m s)
    (insertEntry-all (c , t) q m z nz)

Removing tokens: filtering, deletion and policies

filter∞ P? v keeps the tokens of v whose key satisfies the decidable property P. Removing entries from a list keeps it sorted and keeps every property of all its entries, so the result is well-formed.

filterEntries : ∀ {P : Key → Set} → U.Decidable P → List Entry → List Entry
filterEntries P? = List.filter (P? ∘ proj₁)

filterEntries-linked
  : ∀ {P : Key → Set} (P? : U.Decidable P) kvs
  → Linked _<ᵉ_ kvs → Linked _<ᵉ_ (filterEntries P? kvs)
-- `<ᵉ-trans` is eta-expanded, as its implicit entries can't be inferred through `proj₁`
-- once `_<ᵉ_` unfolds.
filterEntries-linked P? _ =
  Linked.filter⁺ (P? ∘ proj₁) (λ {e₁ e₂ e₃} → <ᵉ-trans {e₁} {e₂} {e₃})

filterEntries-all
  : ∀ {P : Key → Set} {Q : Entry → Set} (P? : U.Decidable P) kvs
  → All Q kvs → All Q (filterEntries P? kvs)
filterEntries-all P? _ = All.filter⁺ (P? ∘ proj₁)

filter∞ : ∀ {P : Key → Set} → U.Decidable P → Value∞ → Value∞
filter∞ P? (mkValue∞ m s z) =
  mkValue∞
    (filterEntries P? m)
    (filterEntries-linked P? m s)
    (filterEntries-all P? m z)

delete∞ c t v removes the token t of the currency c from v, if it is present.

delete∞ : CurrencySymbol → TokenName → Value∞ → Value∞
delete∞ c t = filter∞ λ k → ¬? (k ≟ᵏ (c , t))

keepPolicies∞ ps v keeps the tokens of v whose currency symbol is in ps, and dropPolicies∞ ps v the others.

keepPolicies∞ : List CurrencySymbol → Value∞ → Value∞
keepPolicies∞ ps = filter∞ λ (c , _) → c ∈? ps

dropPolicies∞ : List CurrencySymbol → Value∞ → Value∞
dropPolicies∞ ps = filter∞ λ (c , _) → c ∉? ps

Looking up the quantity of a token

lookup∞ c t v is the quantity of the token t of the currency c in v, or zero if v does not contain it. Since the quantities in a value are non-zero, a quantity of zero means exactly that the token is absent.

lookupEntry : Key → List Entry → Quantity
lookupEntry k kvs = maybe′ proj₂ 0ℤ (List.find (λ (k' , _) → k' ≟ᵏ k) kvs)

lookup∞ : CurrencySymbol → TokenName → Value∞ → Quantity
lookup∞ c t v = lookupEntry (c , t) (Value∞.map v)

Scaling quantities

scale∞ n v multiplies every quantity of v by n. Scaling by zero gives the empty value. Otherwise, scaling keeps the keys, so it keeps them sorted, and the product of two non-zero integers is non-zero.

scaleEntry : Quantity → Entry → Entry
scaleEntry n (k , q) = k , n ℤ.* q

scaleEntries : Quantity → List Entry → List Entry
scaleEntries n = List.map (scaleEntry n)

scale∞ : Quantity → Value∞ → Value∞
scale∞ n (mkValue∞ m s z) with n ℤ.≟ 0ℤ
... | yes _   = empty∞
... | no  n≢0 =
  mkValue∞
    (scaleEntries n m)
    (Linked.map⁺ {R = _<ᵉ_} {f = scaleEntry n} s)
    (All.map⁺ (All-map (λ q≢0 → [ n≢0 , q≢0 ]′ ∘ ℤ.i*j≡0⇒i≡0∨j≡0 n) z))

Scaling keeps every property of the keys.

scale∞-keys
  : ∀ {P : Key → Set} n v
  → All (P ∘ proj₁) (Value∞.map v) → All (P ∘ proj₁) (Value∞.map (scale∞ n v))
scale∞-keys n (mkValue∞ m _ _) a with n ℤ.≟ 0ℤ
... | yes _ = []
... | no  _ = All.map⁺ a

Negating quantities

negate∞ v negates every quantity of v. Negation is scaling by -1.

negate∞ : Value∞ → Value∞
negate∞ = scale∞ ℤ.-1ℤ

Comparing quantities: containment

contains∞ v₁ v₂ checks that v₁ contains v₂, that is, that every entry (k , q) of v₂ has q ≤ lookupEntry k in v₁. When the quantities of v₁ are non-negative, this means that v₁ holds at least as much of every token as v₂ does (see Builtin.Value.Base.Properties). The builtin requires the quantities of both values to be non-negative.

ContainsEntries : List Entry → List Entry → Set
ContainsEntries kvs₁ = All λ (k , q) → q ℤ.≤ lookupEntry k kvs₁

containsEntries? : ∀ kvs₁ kvs₂ → Dec (ContainsEntries kvs₁ kvs₂)
containsEntries? kvs₁ = all? λ (k , q) → q ℤ.≤? lookupEntry k kvs₁

contains∞ : Value∞ → Value∞ → Bool
contains∞ (mkValue∞ m₁ _ _) (mkValue∞ m₂ _ _) = isYes (containsEntries? m₁ m₂)

NonNegative : List Entry → Set
NonNegative = All λ (_ , q) → 0ℤ ℤ.≤ q

nonNegative? : ∀ kvs → Dec (NonNegative kvs)
nonNegative? = all? λ (_ , q) → 0ℤ ℤ.≤? q

Conversion to a flat list of triples

toFlatList∞ forgets the invariants, giving the entries of a value as a flat list of triples.

toFlatList∞ : Value∞ → List (CurrencySymbol × TokenName × Quantity)
toFlatList∞ v = List.map (λ ((c , t) , q) → c , t , q) (Value∞.map v)
